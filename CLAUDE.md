# Gordium

## What Gordium is

A co-pilot inside Rhino for architects. It knows every zoning rule a building must follow and checks each design edit against them (pass / fail / needs review). Later it proposes design options and learns each firm's style.

- **End goal:** an architect describes what they want and gets a final design in Rhino that is legal, meets the brief, and looks like their work.
- **Moat:** trusted, approved rules; exact city-specific measurement code; each firm's design memory. Not the AI itself.
- **First city:** City of Ithaca, NY (not the Town of Ithaca, which has its own code). Residential districts first.
- **Design doc:** https://claude.ai/code/artifact/d980dd22-6b2e-4090-bcc4-d02c871b8a7b (tabs: Plan · How it's built · Research)

## Core principles (do not break these)

1. **Compile, then freeze.** Documents are turned into rules once per code version. Approved rules are frozen as data.
2. **AI drafts, architects approve.** AI may draft labels and formulas from documents. Nothing is used until an architect approves it.
3. **The checker never uses AI.** Checking a design is plain code reading frozen rules. Same design + same rulebook = same answer.
4. **Never a false pass.** Missing data, unclear rules, or failed measurements give "needs review", never "pass".
5. **Everything is traceable.** Every rule records its source file (with fingerprint), page, exact position, quote, who approved it, and when.
6. **Measurement definitions are code written by engineers**, tested on real models. AI never writes them.

## Repository layout

```
regulations/     DATA: rule documents and rulebooks (no code)
  document_extraction_guide/   how we turn any regulation document into rules
  jurisdictions/<state>/<place>/   numbered steps 1–7, plus jurisdiction.yaml (the place's settings: name,
                                   boundary codes, coordinates, time zone, law files, its adapters), read only
                                   through the registry (rule_format/place.py); see docs/adding_a_place.md
    1_source_documents/   originals, never edited (+ sources.yaml)
    2_extracted_text/     generated by code, never hand-edited
    3_section_labels/     which part of which doc is Rule / Flag / Reference / Not for checking
    4_term_definitions/   how this place defines height, story, grade plane…
    5_zoning_rules/       THE RULEBOOK, one file per district; architects approve
    6_coverage_report/    generated proof nothing was skipped
    7_published_rulebooks/ frozen versions the checker uses; never changed once made
packages/        LOGIC: one package per job (rule_format, document_extraction, site_lookup,
                 model_labeling, model_measurement, envelope_builder, design_checker)
apps/            PRODUCTS people use (command_line, rule_review_app; later rhino_plugin, api)
test_data/       answer_keys/ (architects' hand-checked rules), test_sites/ (real lots + models + expected results)
docs/            design notes, decisions/ (one short file per big decision)
```

Planned but not created until their code is written: `packages/ai_designer`, `packages/design_memory`, `apps/rhino_plugin`, `apps/api`.

## Conventions

- Lowercase names with underscores everywhere. Dates as YYYY-MM or YYYY-MM-DD so files sort.
- District files named exactly as the city writes them (`R-1b.yaml`).
- Each package has a README, its code, and its own `tests/`.
- Python for packages. Rhino plugin language (C# vs Rhino 8 Python) is not decided yet.

## How we work

- Talk through the approach before building anything non-trivial; get agreement first.
- When Ben shares files, decide whether each is relevant and file it in the right place (unchanged, original name). Say where each went.
- Explain things in plain, simple language. The audience includes architects and shareholders.
- Ground claims in the actual files and documents; cite where information came from.
- When unsure about a zoning interpretation, flag it for the architects instead of guessing.

## Git workflow

- Feature branches → PR → CI → Ben merges. Never push directly to main. **Never merge a PR; Ben merges every PR himself.**
- Stack dependent work with Graphite: `gt c -m "msg"` to commit, `gt s` to submit. Each PR must be independently reviewable **and evaluable**: it states how we know it is right, and CI proves it.
- No squash merges (`--merge`, keep history). Small cohesive commits with prefixes `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`.
- Don't commit or open PRs unless Ben asks or invoked `/autopilot`. Even in autopilot, **before each commit** stop and tell Ben: what's being committed, what's done so far, what's next, why now, and why it's the right approach. Wait for his OK.
- Every PR description has a **Test Plan with evidence**: each check run (pytest, rule validation, extraction reproducibility) with its result, plus the eval that proves the PR's output is correct.
- After opening a PR, watch CI until green. If a check fails, say which, why, and the fix.
- Run `/review` before calling a PR ready. For bigger PRs also run an independent review agent with no conversation context. Reviews are two-pass; label findings **confirmed** or **suspected**.
