# Gordium

## What Gordium is

A co-pilot inside Rhino for architects. It knows every zoning rule a building must follow and checks each design edit against them (pass / fail / needs review). Later it proposes design options and learns each firm's style.

- **End goal:** an architect describes what they want and gets a final design in Rhino that is legal, meets the brief, and looks like their work.
- **Moat:** trusted, traceable rules; exact city-specific measurement code; each firm's design memory. Not the AI itself.
- **First city:** City of Ithaca, NY (not the Town of Ithaca, which has its own code). Residential districts first.
- **Design doc (the one place for how Gordium works and why):** https://claude.ai/artifact/BMkp3eyrgemdqcwhi9oFxf (Gordium System Map: high-level flow, one rule end to end, each stage, PRs, key decisions). The original plan (Oct 16, superseded): https://claude.ai/code/artifact/d980dd22-6b2e-4090-bcc4-d02c871b8a7b

## Core principles (do not break these)

1. **Compile, then freeze.** Documents are turned into rules once per code version. Approved rules are frozen as data.
2. **AI drafts, code checks.** AI may draft labels and formulas from documents; code verifies every draft (exact quotes, valid formulas, worked examples, provenance). Human approval is deferred for now (decided 2026-10-19): rules stay marked draft, and the approval fields stay in the format, unused, so a reviewer can be added later without a rebuild. A spreadsheet export of the rules, with links to the city's exact words, is how people read and check them.
3. **The checker never uses AI.** Checking a design is plain code reading frozen rules. Same design + same rulebook = same answer.
4. **Never a false pass.** Missing data, unclear rules, or failed measurements give "needs review", never "pass".
5. **Everything is traceable.** Every rule records its source file (with fingerprint), page, exact position, quote, and every change after the AI's draft (who, when, why).
6. **Measurement definitions are code written by engineers**, tested on real models. AI never writes them.

## Conventions

- Lowercase names with underscores everywhere. Dates as YYYY-MM or YYYY-MM-DD so files sort.
- District files named exactly as the city writes them (`R-1b.yaml`).
- Each package has a README, its code, and its own `tests/`.
- Python for packages. Rhino plugin language (C# vs Rhino 8 Python) is not decided yet. The Revit add-in is C# talking to the Python worker (Ben, 2026-11-05); it is built for .NET 8 (Revit 2025–2026) and .NET 10 (Revit 2027), to confirm in the Windows trial (docs/revit/windows_trial_runbook.md).

## How we work

- Talk through the approach before building anything non-trivial; get agreement first.
- When Ben shares files, decide whether each is relevant and file it in the right place (unchanged, original name). Say where each went.
- Explain things in plain, simple language. The audience includes architects and shareholders.
- Ground claims in the actual files and documents; cite where information came from.
- **One design document, kept high level.** The System Map linked at the top of this file shows how Gordium works at a glance: the logic flow, each stage, the key decisions in one line each, how we know, what's open. Any PR that changes the flow or a key decision updates it. Detailed reasoning (why, alternatives rejected) and code-level detail live in the repo docs (`docs/`) and PR descriptions, linked rather than repeated.
- **Resolve before asking.** When the law seems unclear, never guess, and never go straight to the architects. In order:
  1. **The whole law:** read every section the term index lists for the term and its synonyms (setback/yard, overhang/projection/eaves, escape window/emergency escape and rescue opening…), not just its definition.
  2. **Research, ranked:** (1) the governing code's own text (Ithaca's zoning code; for egress, the NYS Residential Code as adopted); (2) official interpretations of it (Ithaca's Board of Zoning Appeals decisions; for egress, NY State's code interpretations); (3) commentary on the same wording (NYS Uniform Code, IBC/IRC commentary); (4) other places' codes. Cite every source (quote + section, or URL + date).
  3. **Classify:** *answered by the law* → record the answer with its citation; *strong common practice* → record Gordium's stated reading with its sources (always shown to the architect as a reading to confirm); *genuinely unclear* → an open question for the architects or the City zoning office, recording what was searched and why it's still open.
  4. An answer from the City or the architects (who, when, which project) outranks Gordium's reading and replaces it.

## Git workflow

- Feature branches → PR → CI → Ben merges. Never push directly to main. **Never merge a PR; Ben merges every PR himself.**
- Stack dependent work with Graphite: `gt c -m "msg"` to commit, `gt s` to submit. Each PR must be independently reviewable **and evaluable**: it states how we know it is right, and CI proves it.
- No squash merges (`--merge`, keep history). Small cohesive commits with prefixes `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`.
- Commit and push to PR branches freely; no approval needed per commit. **Ben approves at merge time.** Keep Ben informed with short updates on results, decisions he needs to make, and problems, not every commit.
- **PR descriptions are written so anyone can follow them** (an architect, a shareholder, someone who has never coded): follow `.github/pull_request_template.md`. Define every technical word, list what was built in everyday language, walk through one real example start to finish.
- Every PR description has a **Test Plan with evidence**: each check run (pytest, rule validation, extraction reproducibility) with its result, plus the eval that proves the PR's output is correct.
- Run only targeted tests locally (the packages a change touches); the full suite runs on GitHub CI.
- After opening a PR, CI must go green before it merges. Agents finish their review loop, report and exit; they don't stay alive waiting on CI (a shell script does the waiting). If a check fails, say which, why, and the fix.
- At most 3 agents run at once (a 16 GB Mac that also runs Rhino and the tests).
- Repo slash commands live in `.claude/commands/` (`/plan`, `/implement`, `/autopilot`, `/review`, `/debug`, `/explain-simple`), tailored to Gordium.
- Run the `/review` **loop** on every PR before declaring it ready. It is not a single pass: each round runs a cold reviewer with no conversation context plus independent skeptics per finding (2 for anything that could cause a false pass: rules, measurement, pass/fail; 1 for UI or wording; a finding is **confirmed** only if it survives adversarial verification); every confirmed finding gets fixed and pinned with a test that fails on revert; rounds repeat until one returns zero confirmed (cap 4). **Generated reports** (large tables made by code, such as the coverage audit) pass once a round confirms no wrong content; confirmed display or wording findings in such a round are fixed or listed as to-dos in the PR (Ben, 2026-10-27). The in-session review runs alongside (it knows the intent, which the cold agents don't) and its findings go through the same skeptics before they count. Fixes introduce bugs, which is why it loops.
- **Large or design-level changes get a review round before they are committed** (`/review` with `uncommitted: true`); small fixes are committed, then re-checked by the next round. Nothing reaches `main` until a round comes back clean and Ben merges.
- **Each PR's review covers only that PR's own changes** (base = the PR below it). A problem found in code a lower PR added is fixed in that lower PR, through its own review loop, then carried up the stack.
- **Confirmed → fix, any tier, without asking.** "Not sure" is a to-do, not a label: dig until it's confirmed or refuted. Only a genuine question of intent goes to Ben, and zoning or egress interpretations still unclear after "Resolve before asking" go to the architects, in plain English with the evidence of what was tried. This applies in `/review` and `/autopilot` alike; `/autopilot` runs the loop on every PR it pushes before reporting done.
