# Rules for each part: one result per bedroom, window and stair (2026-11-12)

**Purpose:** how a rule says "for each bedroom / escape window / stair", and how the checker answers it, one row per part.\
**For:** engineers changing `rule_format` or `design_checker`; architects reading the panel.\
**Kept current by:** the engineer who changes `rule_format/parts.yaml`, `rule_format/parts.py`, `design_checker/each_part.py` or how `rule_drafting` drafts a rule for each part, in that PR.

Egress step 2 of the [egress design doc](https://claude.ai/artifact/SzJvw7FdbsdfGMqUHxspFU) (§9, "Rules per part"). Zoning rules are about the whole lot: one rule, one answer. Building-code egress rules repeat: *every* sleeping room needs an escape opening, *every* stair has a riser limit. The architect must be told *which* one fails ("Bedroom 2: escape opening net clear area 5.1 sq ft, needs ≥ 5.7 sq ft"), not just "a window somewhere fails".

The real egress rules are not written yet (step 1, bringing in the code text, waits on the copyright decision). Every rule in this PR's tests is **synthetic**, marked so, and quotes made-up text, never the code.

## Decision

1. **Part kinds are a fixed list engineers write**, `rule_format/parts.yaml`, like `measures.yaml`: each kind's name, meaning, the measures each part of that kind carries (with units), and for a part that sits inside another, which kinds it can sit `within`. First kinds: `sleeping_room`, `emergency_escape_opening` (within a sleeping room), `stair`, `egress_door`. A part's measure names are unique across every kind and never a building measure's name, so a formula's names can't mean two things.
2. **A rule says what it repeats over** with three new optional fields:
   - `for_each: <part kind>`: one result per part of that kind.
   - `within: <part kind>` (optional): the parts are grouped by the part they sit in, so the rule is "for each escape opening *of each sleeping room*".
   - `when_none:` what the law says when there is nothing to check: `fail`, `needs_review` or `not_applicable`. **Required** on every per-part rule, and never `pass`. With `within`, it is the answer for a sleeping room with no escape opening (each such room gets its own row, named); without, the answer when the building has none of that kind (no stairs: not applicable).
   A rule's formulas (and its worked examples' values) may use the building's measures (`use`, `stories`, …) and its own part kind's measures, nothing else. Validation refuses an unknown part kind, a `within` the kind can't sit in, `within` or `when_none` without `for_each`, a missing or `pass` `when_none`, a part measure of another kind, and a part measure in `applies_when` when `when_none` isn't `not_applicable`: a rule that must find a part says which parts differ inside its `check` (`opening_net_clear_area >= (5.0 if opening_at_grade else 5.7)`), so it can't rule out every part of a room and leave the room with no row that fails. Worked examples are small designs, checked by the checker's own rows (point 9).
3. **One row per part.** `rule_format/parts.py` runs each part's values (the building's plus the part's own measures; a part can't change a building value) through `outcome()`'s own evaluation (`part_outcome`, the rule's per-part fields set aside), so missing values and three-valued logic mean what they mean for zoning: a part missing a measure that could change its answer needs review; one that fails whatever that measure is (`5.1 sq ft` and the height missing, against "area ≥ 5.7 and height ≥ 24") fails. The "fails whatever the missing number is" proof of 2026-10-21 applies to each part too (point 10). `design_checker/each_part.py` (plain code, no AI) names the rows. Each row carries the rule, the part's kind, id and name, the part it sits in, the result and a line naming the part ("Bedroom 2 › Window 5: net clear area 5.1 sq ft, needs ≥ 5.7 sq ft").
4. **Never a silent pass.** Each of these gives a row of its own, never nothing:
   - the parts of a kind the rule needs (its `for_each` kind, and its `within` kind if it has one) were not read at all (not given, as opposed to an empty list): **needs review**, "not read yet";
   - a part with no id, two parts with one id, a part `within` a part that isn't there, or a part that isn't a mapping: **needs review**, naming the problem;
   - a sleeping room whose escape opening is there but can't be read (or an opening that doesn't say which room it is in): **needs review** for that room, never "none";
   - none to check: the rule's own `when_none` (and with `within`, a building with no sleeping rooms at all: **not applicable**, since nothing the rule talks about exists).
5. **The rule's answer and the design's** follow `present.state` (PRs #81, #82): a rule does not comply if any of its rows fails, else needs review if any does, else complies if at least one row complies; a rule with only not-applicable rows is not applicable. Rows are shown as panel items (status `does_not_comply`/`needs_review`/`complies`; not applicable rows left out, as today), so the design's overall state is `present.state` over zoning and part rows together. Nothing counted is needs review, never complies (PR #81; until it merges, `each_part` never adds a complying item for a rule that checked nothing).
6. **A per-part rule never answers as a whole-building rule.** The public `outcome()` given a rule with any per-part field says needs review, so code that doesn't know about parts (the project report, the envelope, `check.row_verdict`) can never pass one. Only `parts.part_outcome` (validation's worked examples, and the checker's rows) answers one part.
7. **Interior not started is said, and counted.** When no parts are given at all (the interior isn't being checked), the per-part rules give one counted item, "Interior: not checked yet", needs review. The design is then never shown as complying with rules nobody checked. In a place's check this is now egress's "waiting" item (item 12): Ben decided (2026-11-12) that zoning and egress are two separate results, so zoning's own section may say complies during massing while the design as a whole does not.
8. **Nothing else changes.** Rule files have no format version; the new fields are optional, so every existing rule file means exactly what it did. The approval fingerprint adds the new fields only when a rule has them, so every existing fingerprint is unchanged (pinned by a test). `7_published_rulebooks/` holds no published rulebook yet; nothing in it changes. The rules spreadsheet (`rule_export`) gains a "For each part" column ("for each emergency escape opening · within each sleeping room · if none: fail"), empty for every zoning rule; nothing else in it changes. The site description (`gordium.site/1`) is unchanged: tests give parts to the checker directly.

9. **Worked examples are small designs** (egress step 3a). A per-part rule's example gives the building's measures (`given`), its parts as the checker is given them (`parts`), every row the rule must give (`rows`: the part's id, the id of the part it sits in, the result; a row about no one part, like a room's "no escape opening", leaves `part` out) and the rule's one answer (`expect`). Validation runs them through `parts.rows` itself, so an example proves the rows the architect will see, not just one part's formula. At least one example must show `when_none` (a row for nothing to check whose answer is the rule's `when_none`): the law's answer for "none" is the part most easily got wrong, so a per-part rule without such an example is refused (a flag too). A rule (not a flag) also needs a part that passes its check and a part that fails it: a "none" row fails whatever the check says, so it can't stand in for a failing part (review round 1: with it as the only failing example, a check every part passes was kept). A part's measure in `given`, a part of a kind the rule doesn't read, another kind's measure on a part, and `parts`/`rows` on a whole-building rule are refused.
   ```yaml
   examples:
     - given: {}                       # the building's measures
       parts:
         sleeping_room: [{id: br1}, {id: br2}]
         emergency_escape_opening: [{id: w1, within: br1, measures: {opening_net_clear_area: 6, opening_net_clear_height: 30, opening_at_grade: false}}]
       rows: [{part: w1, within: br1, outcome: pass}, {within: br2, outcome: fail}]   # Bedroom 2 has none: when_none
       expect: fail
   ```
   **Drafting** (`rule_drafting`) runs the same code checks on a per-part draft as on a zoning one: every quote is the source's exact words, every typed number is written in it, and the examples are checked by the rows above. Where it tests whether a chart number decides anything (changing it changes some example), it compares the examples' rows and answers (`parts.worked_example`), never `outcome()`, which says needs review for every per-part rule, so no number could ever be shown to decide. The answer's shape and the instructions gain the per-part fields only when a run asks for them (`for_parts`); a zoning run sends exactly what it always did.
10. **"Fails whatever the missing number is" applies to each part.** One proof, `rulebook.unknown_settings`, shared by the checker's zoning rows (`check.fails_whatever`) and `parts.rows`: a part missing a measure the check is provably truest at 0 for (only +, −, max/min and positive multiples of it, compared with < ≤ > ≥) is tried at 0, a missing yes/no both ways; if it fails under every setting, it fails whatever the missing value is ("Stair 1: SYNTHETIC stair headroom: does not comply whatever the riser height (not measured)", for 70 in against `72 + riser`). Safe: it only ever turns needs review into fail, never into pass; a value given but unusable (NaN, below 0), or a missing one in `applies_when` or `review_when`, gets no proof. Parts carry one value or none (no readings), so the reading set the zoning proof also ranges over has nothing to add.
11. **Massing code leaves the inside alone.** A district rulebook should hold no per-part rule (they belong in the building-code rulebook), but if one is there: the envelope (`envelope_builder/envelope.py`) skips a per-part rule that reads nothing it shapes, and draws **no envelope** (with a note) for one that reads a yard, the height or the building area, since that can't be read as a whole-building limit and ignoring it could draw a box larger than a rule allows. The start box's questions (`check._read_for`) take a per-part rule's building facts (asked like any rule's: unasked, they'd leave its rows needing review) and never its parts' measures, which come from the interior.

12. **Egress switched on (2026-11-14).** A place's check (`check.check_site`, and `check_description` and `check` for the hosts) also runs the rules of every state law the place inherits (`design_checker/egress.py`): Ithaca's, New York's house code. One check, one result, grouped by law: the view's `sections` are "Zoning (City of Ithaca)" and "Egress (NY State Residential Code 2025)" (the state's `results_title`), each with its own state; the law's items are one panel group of their own, after zoning's; the design's state is `present.state` over both, and its line says each law apart ("Zoning complies · Egress: 1 does not comply · 40 need review"; zoning gives its counts only when it does not comply).
    - **Where the interior comes from:** an interior description (`gordium.interior/1`, [its format](../interior/interior_description_format.md)) given beside the site description, never inside it (`gordium.site/1` and the worker protocol are unchanged: no host sends one yet; `python -m design_checker <model> <facts> --interior <house.yaml>` does). It is measured by `model_measurement.interior` and its parts go to the rows above.
    - **No interior read** (none given, or one whose list of rooms is empty; one that leaves `rooms` out needs review, "the rooms weren't read"): each law gives one item, "Egress: waiting, no rooms drawn yet", not checked, its section's state `waiting`. Never a pass and never a fail; it holds the design at needs review at best, and the line ends "Egress waiting: no rooms drawn yet" (the waiting item's own reason), so it never reads as all complying.
    - **The massing headline: choice B (Ben, 2026-11-15).** Question #106 left open: while zoning complies and egress only waits for rooms, should the headline stay amber needs review (A) or read calmer (B)? Ben chose B. The headline reads "Zoning complies · Egress waiting: no rooms drawn yet", shown in a neutral grey "waiting" style, not amber, with no "?" mark. The check marks this case `waiting_only` (`egress.add_to_view`): zoning complies, at least one law waits, and every law waits or complies. Anything else (zoning fails or needs review, a law fails or needs review) keeps the usual red or amber headline. Only the look changes: the design's state stays needs review, never complies, in the JSON, the command line, the Rhino panel and the Revit worker's answer. The grey is `rhino_logic.headline_state`/`headline_rgb` (host_core/panel_words.py); the Revit add-in has no coloured headline yet, so it shows the state (needs review) as before. Tests: `design_checker/tests/test_waiting_headline.py`.
    - **Each row** names its part ("Bedroom 1 › Window 1", the room named for a window even where the rule isn't grouped by room), the rule's code section ("R319.2.3", from the state's sections file) and the rule's exact quote, and for a fail the change the rule asks ("sill height 48 in, needs ≤ 44 in"). Its id is the rule, the room and the part (`general.r319_2_3_escape_opening_max_sill_height@bed1/w1`), the same at every check.
    - **A measure the measuring gave no value, or a reason** (`not_measured`) needs review with that reason ("sill height not measured: an awning window's clear opening depends on …"); a value that also carries a reason is not used (`each_part.cautious`). As for every part, a part that fails whatever the missing value is fails (item 10): never a pass.
    - **The state's rules are used only if they pass the rule checks** (`rule_format.rulebook_file_problems`, as zoning's rulebook must): otherwise one item, needs review, naming the problem, with or without rooms drawn (never hidden behind "waiting"); zoning is still checked. An interior description that can't be read gives needs review, never waiting. An escape opening marked in a room that isn't a sleeping room (the measuring leaves it out) gets its own needs-review item: it may be a basement's or an attic's, not read yet.
    - **Not read from the drawing yet:** handrails (`handrail`), open sides (`open_side`: the guard rules) and sleeping lofts (`sleeping_loft`), and the basements, habitable attics and loft rooms an escape opening may sit in. The interior measuring gives guards as its own kind (`guard`), not yet handed to the rules. Every rule over those kinds needs review ("the open sides aren't read yet"), never a pass.
    - **A state rule not written for each part** (no `for_each`) is never dropped: it needs review, "not checked, check it by hand". A `state.yaml` that can't be read, or a `results_title` that isn't words, is a problem of the law's (needs review), never a crash of the check. A saved report says which interior it was checked against ("Interior checked: sha256 …", or "Interior: none drawn yet").
    - Tests: `design_checker/tests/test_egress.py`.

## How parts will arrive (later, step 4)

A later site description version adds `parts: {<kind>: [{id, name, within?, measures: {...}, from: {...}}]}` per building, a flat list by kind, each part pointing at the part it sits in by id, each measure with where it came from (read from the drawing, suggested, stated by the architect: the three levels in the design doc §8). `parts` absent means interior checking is off (the architect hasn't run `GordiumInterior`): no part is checked, so the panel never warns "bedroom has no window" during massing, and the one "Interior: not checked yet" item (point 7) keeps the design from reading as complying. A kind absent once interior checking is on means "not read yet" (needs review); an empty list means "read, and there are none".

## Why

- **The law's own words decide "none".** "Each sleeping room shall have an escape opening" makes a room with none a fail; "each stair" makes a house with no stairs not applicable. One fixed default would be wrong for one of them, so the rule must say.
- **Designated escape openings, not every window.** The code asks for *an* escape opening per sleeping room, not that every window qualify. So a per-opening rule runs over the openings marked as the room's escape opening (a part kind of its own), and the same rule's `when_none: fail` gives a room with none its own failing row; no separate count, which a reader could get out of step with the openings it read. Checking every window would fail a good bedroom for its small second window.
- **Same `outcome()` for everything.** Reusing the zoning evaluator keeps one meaning of missing data and one meaning of pass; parts add only the loop and the naming.

## What we rejected

- **Count measures on the building** (`sleeping_rooms_without_escape_opening == 0`): passes or fails but can't say which room.
- **A per-part loop inside formulas** (`all(o.area >= 5.7 for o in openings)`): a new formula language, harder to check, and still one answer per rule.
- **"At least one window in the room qualifies" as a quantifier** for now: needs one rule to look at all the room's windows together and say which comes closest. Possible later as `need: any`; designating the escape opening is how the code and architects already think about it.
