# The interior description says what the house has none of; facts it holds become measures (2026-11-16)

**Purpose:** how the interior description (`gordium.interior/1`) states that a house has none of a kind of part (no ramps, no sleeping lofts), how that turns rules into "not applicable" without ever hiding them, and which facts already in the description become measures.\
**For:** engineers changing `model_measurement.interior`, `design_checker/egress.py` or `each_part.py`, a host reader's authors (Rhino, Revit, IFC), and Ben.\
**Kept current by:** the engineer who changes those files, in that PR.

## Why

PR #108 ran the whole egress rulebook on a real house (`test_data/real_houses/orangetown_ny_80_south_william/`): all 115 rules needed review, 52 of them ones a person settles from the drawings. 33 of those were about kinds of part the format had no way to say the house doesn't have (category F), 4 were facts the description already held or could hold but the measuring didn't turn into the rule's measure (M), 1 was guards (G), 12 stair geometry the drawings don't give (D), 2 rule drafting (R).

## Decisions

1. **Absence is stated, never inferred.** A new top-level list, `has_none`, each entry `{kind, source, reading?}`: "this house has no <kind>", and where that comes from (a sheet and callout, or the architect's own statement in a host). `reading: true` marks a claim that rests on a reading of the law rather than the drawings alone (an unfinished attic is not a habitable attic): it is shown as one to confirm (decision 4). Silence stays what it is today: the kind isn't read, its rules need review. Named `has_none`, not `absent`: house files already use a per-part `absent:` for values the drawings don't give (a note the measuring ignores), and one word with two meanings would invite exactly the mistake this must prevent.
2. **The kinds it may name are a fixed list in code** (`model_measurement.interior.has_none.KINDS`), each with its plain words and what it settles:
   - part kinds (`rule_format/parts.yaml`) the description has no list for: `basement`, `habitable_attic`, `sleeping_loft`, `ramp`, `alternating_tread_device`, `ships_ladder`: that kind's parts become `[]`. A rule for each part of that kind then gives its "none" row (its `when_none`: not applicable for every such rule today, and a rule that must find one would fail, as it should); a rule for the parts *within* that kind (R319.1's escape openings in a basement, habitable attic or loft room) gives its "no basements" row, not applicable whatever its `when_none`, which is right: there is no such space to need one;
   - `sleeping_loft` also settles `loft_room` (R319.1: "the room a sleeping loft is open to" exists only where a sleeping loft does): `[]`, said so; and every stair measured gets `stair_serves_sleeping_loft: false` (no loft, so no stair serves one);
   - `patio_cover`: each escape opening measured gets `opening_into_patio_cover: false` (no patio cover, so no opening opens into one);
   - `deck_porch_or_cantilever_over_escape_opening`: each escape opening measured gets `opening_under_projection: false` (a claim about the openings, since a house may well have a porch that isn't over any of them).
   The five kinds the format already lists (`rooms`, `openings`, `stairs`, `doors`, `guards`) are refused: they are said with their own list (`stairs: []` says none; `rooms: []` is a house not drawn yet, egress waits, so no sleeping rooms is said with `sleeping: false` on each room).
3. **A claim that can't be trusted is a problem, never not applicable.** Each of these is an "Interior drawing" needs-review item, and the kind stays not read: `has_none` not a list; an entry not `{kind, source}`; an unknown kind; no source (empty text); a `reading` that isn't true or false; a key other than `kind`, `source`, `reading` (a mistyped `reading` must never read as settled); a kind named twice; and a **contradiction**: the description also gives a non-empty list of that kind (`ramps: [...]`, `basements: [...]`, the list a later reader will fill). A "no basements" claim is also refused beside a space the description shows below the ground (an opening's `area_well`, or a room's floor or a stair's foot below the highest ground given outside any opening), and a "no sleeping lofts" claim beside a room drawn within another room's height; a value given that can't be read refuses too. These only refuse: they never say "there is a basement" or "a loft". Both are partial (the format doc says where). The deck, porch or cantilever claim (about the openings) has no list to contradict yet; that is said in the format doc.
4. **Not applicable from a claim is shown, never hidden.** Today a not-applicable row is left out of the panel. For a claim, one panel item per kind: "Ramps: not applicable: the description says the house has no ramps (A-2 …)", its detail listing every rule it set aside. Every row a claim settles is tagged with it where the claim is applied (`each_part`: the kind's "none" row, the "no basements" row of a rule within it, or a part whose `applies_when` reads a measure the claim gave and is not applicable only because of it: a spiral stair is not applicable to R318.7.1 whatever a loft claim says), and carries the same words. A row that would pass by reading a measure a reading claim gave (anywhere in the rule) needs review instead: "complies only if this reading is confirmed". The item has a new status, `not_applicable`, that counts toward nothing: never a pass, never holds the design at review (`present._building_items` leaves it out, so `state` and the summary ignore it), it sorts last (`egress.ORDER`, the sheets' `CAUTION`), and a law whose only items are these is still "nothing checked" (needs review). A claim marked as a reading is instead a needs-review item, "Habitable attics: not applicable if this reading is confirmed". The permit sheets print it as a row, "NOT APPLICABLE". Beyond these, no presentation code changes (another branch is changing the panel's grouping and folding).
5. **Facts become measures only by pure derivation** (M). If the fact isn't given, or doesn't decide it, the measure isn't given (with a reason):
   - `door_side_hinged` from a door's `operation`: `side_hinged` yes; `sliding`, `folding`, `pocket` no; `other` not given.
   - `opening_is_door` from an opening's `operation`: `side_hinged_door`, `sliding_door` yes; `casement`, `double_hung`, `single_hung`, `horizontal_slider`, `awning`, `hopper` no (window types by name); `fixed`, `pivot`, `tilt_turn`, `other` not given (each is made as a door too).
   - `opening_door_hinged_or_sliding`: yes for `side_hinged_door` and `sliding_door`; else not given (R319.3 reads it only for a door).
   - **`opening_operable` is not given yet.** It is a pure derivation, but R319.6's rule (`r319_6_addition_sleeping_room_escape_opening`) checks it on the openings of every sleeping room, since a rule for each opening can't read whether its room is new; with it measured, R319.6 would say "complies" on every new house, where the law doesn't apply. Its fix (a rule change through the drafting record, against the answer key's own R319.6 rule) is a question for Ben, not this PR.
6. **Guards stay guards (G is not closed).** The guard rules read `open_side` parts. Turning each `guard` into an open side would list only the open sides that have a guard: an unguarded balcony edge, missing from the list, would let R321.1.1 say "complies". An open side needs its own list (with its drop), which no reader gives yet.
7. **How the hosts fill it:** always from the architect's statement, never from not finding something. Rhino: a "the house has none of" list the architect ticks per kind, with the sheet. Revit knows every element in the model, so it can *propose* a claim (no Ramp elements, no stair of a ladder type), but a ramp drawn as a sloped floor or a ship's ladder as a generic family is invisible to that scan: a proposal is sent only once the architect ticks it, and the source says both ("no Ramp elements in the model; ticked by the architect"). An IFC reader likewise proposes from element types (`IfcRamp`, `IfcStair` of type `LADDER`) and sends a claim only once it is ticked. The Revit add-in's status list doesn't know `not_applicable` yet: it sends no interior today, so it never receives one; before it sends `has_none` it must learn the status (noted in the format doc; the C# isn't changed here).

## How we know it is right

- Tests that fail on revert: silence stays needs review; a claim gives not applicable with its source in the item and the rows; a reading claim is a needs-review item; a claim contradicted by a part list is a problem item and its rules need review; a claim without a source, of an unknown or listed kind, or twice is refused; each derivation, and a missing or undeciding fact gives no measure.
- Orangetown, expected: F 33 → 32 settled (R319.6's basement rule stays: the house has a basement the format can't describe), of which the habitable attic, the ship's ladder and the patio cover (8 rules) through reading claims, still needing review as one item each; M 4 → 2 settled (the front door side-hinged; R319.3, every escape opening a window). `opening_operable` and `opening_below_grade` stay.
- The Orangetown house: `house.yaml` gains the claims its drawings support, each citing its sheet; `hand_check.yaml`'s truths are unchanged, only the predictions move, each toward the truth; the test still refuses any pass where the truth isn't complies, and any not applicable where it isn't not applicable.
- Goldens re-recorded (design_checker, permit_sheets), every status change read: each from needs review to the hand-check's truth.

## Not yet

- `opening_operable` (decision 5), `open_side` (decision 6), `opening_below_grade` (the basement windows), stair geometry (category D: the drawings give none).
- Basements can't be described as present (the format has no basement flag), so R319.6's basement rule stays needs review on a house that has one.
